# 留白髮所 MARGIN — 個案研究

> **概念作品，非真實店家。** 品牌、營運資料與影像皆為虛構示意；價格、時長、營業規則依台灣沙龍實務設定。

## 1. 要解決的問題

美髮客人的決策幾乎都在手機上走完：IG／Google 地圖 → 看作品 → 看設計師 → 看價格 → 預約。
台灣多數沙龍網站在這條路上有三個斷點：

- **作品集雜亂**：每位設計師各自拍，滑下來像五間店
- **預約斷點**：只放電話或 LINE，客人得跳出去再等回覆
- **只有形象沒有信任**：大圖很美，但看不到「誰會服務我」

所以網站只有一個轉換目標：**產生預約**。主要受眾是想換設計師的探索型顧客（約 55%），
他們最怕的是被推銷、被加價、約到沒看過作品的人。

## 2. 把「留白」寫成規格

品牌叫「留白」，留白就不能只是一種感覺。我把它拆成四條可以拿來檢查版面的原則：

1. **一屏一件事**：每個區塊只傳達一個訊息
2. **減法優先**：新增元素前，先問能不能拿掉別的
3. **留白是主角**：寧可頁面長，不要擠
4. **一個主按鈕**：每個區塊最多一顆

視覺再收斂成幾條硬規則：只有黑白加一個強調色 `#C8351C`、無漸層無陰影、圓角一律 0、
hover 只降不透明度。強調色後來刻意**只當狀態色**——目前所在頁、欄位錯誤、接不下的日期、需要漂髮——
不拿來當行動按鈕。按鈕也是紅的，這個訊號就失效了。

## 3. 關鍵決策與代價

完整 12 條記在 PRD §12，這裡挑最能說明取捨的六條。每一條都寫了放棄什麼。

### 不用 LINE 預約（D-01）

LINE 是台灣客人最熟悉的預約管道。但訊息預約會讓設計師在服務中不斷回訊息，
直接違反「一次只服務一位客人」的定位，也留不下可分析的結構化資料。
代價是可能流失一部分習慣 LINE 的客人，所以保留電話作為退路。

### 自建五步驟預約，不嵌第三方 widget（D-02）

嵌 widget 半天就好，自建約兩週。但預約是全站唯一的轉換行為，
把最重要的一頁交給別人的視覺，省下的時間不划算。

### 價格全公開（D-03）

主要受眾最怕被加價。公開完整價目（含長髮加價與職級價差）直接處理這個恐懼，
代價是失去詢價制的報價彈性，所以一律標「起」價並寫明加價條件。

### 拿掉麵包屑和 Header 的預約按鈕（D-09）

站的實際深度只有兩層，麵包屑不提供新資訊；每頁底部已經有預約區塊，
Header 再放一顆，同一個畫面就有兩個主鍵。

這是代價最大的一條：預約入口少了一個。對策是手機的常駐預約列，
並事先寫好判斷條件——上線後預約 CTA 點擊率若撐不起 8%，優先把 Header 按鈕加回來。

### 不做 Before／After（D-11）

Before／After 對高單價客人最有說服力，但手上沒有任何「施作前」的素材。
拿兩張不相干的照片湊，在美髮業就是不實廣告，比不做更糟。
改由作品頁的漂髮標示與色號、服務頁寫明「不接哪些髮況」來分擔，並記下接上實拍後要優先補回。

### 預約後端用 Google 日曆，不用 SimplyBook.me（D-12）

這條是實作時推翻原規格的。「同時段只服務一位客人」剛好等於「一位設計師一本日曆」；
設計師本來就在用日曆，店家不必再學一套後台。營業時間、公休、提前一小時、每個項目的時長
仍然只寫在自己的程式裡，Google 只回答「這位設計師哪幾段時間已經有事」。

代價是沒有原子性的訂位：查空檔到送出之間，時段可能被別人約走。所以流程裡必須設計這個狀態（見第 4 節）。

設計與實作階段推翻規格的地方，我都回填成決策記錄，不讓它只存在程式碼裡。

## 4. 預約流程

選設計師 → 選服務 → 選時段 → 填資料 → 確認。
右側摘要會把當步剛決定的值放大，還沒決定的欄位寫「尚未選擇」，按鈕停用時把原因寫在按鈕下方。

除了順利路徑，我另外設計了三種真的會發生的邊界狀態：

| 狀態 | 畫面 |
|---|---|
| 那天整天排不下 | 日期格轉強調色，直接給三個替代時段 |
| 送出時時段被別人約走 | 跳出對話框說明 |
| 送出失敗 | 導覽列下方出現黑底提示，填好的資料保留，可以重送 |

實作時也修正了原型本身的問題：原型把欄位錯誤的檢查放在「下一步」，
但下一步在填完之前本來就是停用的，所以設計好的錯誤態在原型裡永遠走不到。
改成離開欄位時檢查之後，錯誤態才真的會出現。

## 5. 細節裡的判斷

**壓在影像上的白字，逐張量對比。**
換上 AI 生成的空間照之後，白牆會吃掉白色標題。量法是依版位比例裁圖、疊上漸層、
取標題範圍內最亮的區塊計算。設計師個人頁在 901px 寬最低只有 1.6:1，頁尾收尾區塊 1.7:1，
都低於大字的 AA 門檻 3:1。調整漸層後全站最低 3.4:1；設計師頁在手機改用素材原本的 16:9，
避免為了壓住文字把整張照片壓黑。

**影像的像素要花在對的地方。**
Gemini 的輸出固定約 100 萬像素，只換長寬比。所以生圖前先對版位比例：
同樣 1MP，比例出錯的圖裁完，可用像素少一半。設計師頁的 Hero 與卡片頭像也拆成兩張——
卡片要看得到臉，Hero 要的是左側留白，讓大名字壓在上面。

**分頁圖示用單角標誌。**
分頁圖示只有 16px，照標誌規範用簡化的單角版，並加白底，避免在深色模式的分頁列上消失。

## 6. 上線前的整理

- **標示虛構品牌、不讓搜尋引擎收錄。** 店址、電話和結構化資料都寫得像一間真的店，
  不標示就可能被當成真店家。頁尾與預約流程都加上聲明，全站設定 noindex。
- **資安掃描。** 對公開的預約與應徵 API 做了一次掃描，找到 5 項（沒有高風險），都已修正：
  會讓整站卡住的 email 驗證回溯、可以偽造 IP 繞過的流量限制、
  借網站的寄件網域寄釣魚信（確認信拿掉備註、姓名限長不收網址、同一信箱一天最多 3 封）、
  直接呼叫 API 約到週一公休日。每一項都先重現、修完再用同樣的方式確認擋下來。

## 7. 還沒做完的

- 影像全是示意，作品照是 Unsplash 佔位；真的上線需要實拍與拍攝同意
- 月曆固定在 2026 年 9 月，換月還沒接
- 預約通知只有 Email，沒有簡訊
- 首頁 Hero 在 2× 螢幕上只有約 1.1 倍密度，需要更高解析度的素材
- 沒有 Before／After，高單價客人的疑慮目前只靠文字與標示分擔

## 8. 分工與 AI 的使用

| 部分 | 做法 |
|---|---|
| 規格文件（PRD、全站文案、SEO） | 我撰寫，AI 輔助整理與潤飾 |
| 高擬真稿、MARGIN 設計系統 | 我設計，以 Claude Design 輔助 |
| 網站程式 | Claude Code 撰寫；我負責需求、審查、驗收與取捨決策 |
| 影像 | Gemini 生成空間、設計師與服務照；作品照暫用 Unsplash |

程式碼不是我逐行寫的。我在這個專案裡負責的是：定義要做什麼、判斷做出來的東西對不對、
在規格與實作衝突時做決定，並把決定寫下來。每一個 commit 訊息都記錄了改動的原因。
